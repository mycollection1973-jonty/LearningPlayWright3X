The await Keyword — Full Research

A complete reference on the await operator in JavaScript: how it unwraps promises, its control-flow effects, rejection handling, top-level await, and more.

JavaScript · ECMAScript 2017 (ES8) · Baseline: March 2017

1. What is await?

await is an operator (like typeof or new, not a statement) that waits for a Promise to settle and returns its fulfillment value. It turns promise-based asynchronous code into flat, synchronous-looking code.

  • It can only be used inside an async function — or at the top level of an ES module (top-level await).
  • It unwraps promises: await promise produces the resolved value, not the promise.
  • It pauses the surrounding async function without blocking the main thread.
  • The only keyword/operator that can... wait — nothing else in JS offers "pause here until async work finishes, then continue".

2. Syntax

await expression
PartMeaning
expressionA Promise, a thenable object, or any value. Anything else is auto-converted to a resolved promise.
Return valueThe fulfillment value of the promise/thenable; if the expression isn't thenable, its own value.
ExceptionThrows the rejection reason if the promise/thenable is rejected.
Where NOT to use it: await outside an async function (in a plain function or the global scope of a script) throws SyntaxError: await is only valid in async functions. Exception: top-level await inside ES modules is allowed (see §6).

3. What can you await?

The expression is resolved exactly like Promise.resolve() — it is always converted to a native promise, then awaited:

Expression typeHow it's treatedExample
Native PromiseAwaited natively — then() is not even calledawait fetch(url)
Thenable objectWrapped in a native new Promise() that calls its then()await axios(config) (axios returns a thenable-ish adapter)
Any other valueWrapped in an already-fulfilled promise; you get the value itself backawait 20 → 20

Live example — awaiting different kinds of values

async function explore() {
    // 1. await a Promise
    let a = await Promise.resolve("Pass");
    console.log(a);

    // 2. await a plain value (auto-wrapped)
    let b = await 200;
    console.log(b);

    // 3. await a thenable object (any object with a .then method)
    let c = await { then(resolve) { resolve("resolved!"); } };
    console.log(c);

    // 4. identity is preserved for non-thenable values
    let obj = {};
    console.log(await obj === obj);
}

explore();
// Pass
// 200
// resolved!
// true

4. Control-flow effects — the microtask magic

When await is encountered, the awaited expression starts executing and control exits the async function and returns to the caller. When the value resolves, a microtask is scheduled to resume the paused code — even if the promise was already fulfilled.

  • Code after await never runs in the same tick — it always happens later (next microtask at the earliest).
  • await never blocks the main thread; only code that depends on the result is deferred.
  • An async function with no await runs completely synchronously (still returning a promise).

The classic order-of-log example

console.log(1);          // sync

async function test() {
    console.log(2);            // sync part — runs immediately
    await Promise.resolve(); // yields control here
    console.log(3);            // resumes later (microtask)
}

test();
console.log(4);          // sync

// Output order: 1 → 2 → 4 → 3

await splits your function into a "before" part (sync) and an "after" part (scheduled as microtasks). One await can make two otherwise-identical calls interleave:

Live example — how await interleaves two calls

async function foo(name) {
    console.log(name, "start");
    await 0;               // a single await makes the fn async
    console.log(name, "end");
}

foo("First");
foo("Second");

// First start
// Second start
// First end
// Second end
Lesson for QA: every extra await introduces an extra microtask. Use await only when you actually need the resolved value — don't sprinkle it everywhere for fun, it makes code slower and can introduce race conditions.

5. Handling rejected promises

If the awaited promise rejects, the rejection reason is thrown at the await line. Catch it like a normal exception: 

async function login() {
    try {
        const token = await apiLogin();
        return token;
    } catch (err) {
        console.error("Login failed:", err);
        throw err;   // re-throw to fail the test suite
    }
}

No try needed — .catch() before await

const response = await apiCall().catch((err) => {
    console.error(err);
    return "default response";   // fallback value
});
// response = "default response" when the promise rejected
This works because proper promise-based functions return a rejected promise rather than throwing synchronously. If the function can throw synchronously (not a promise API), you must use try/catch.

Live example — rejection handling both ways

async function withTryCatch() {
    try {
        let data = await Promise.reject("503 Service Unavailable");
        console.log(data);
    } catch (err) {
        console.log("caught:", err);
    } finally {
        console.log("cleanup done");
    }
}

async function withCatch() {
    let response = await Promise.reject("Request failed")
        .catch(err => err + " → fallback");
    console.log(response);
}

withTryCatch();
withCatch();
// caught: 503 Service Unavailable
// cleanup done
// Request failed → fallback

6. Top-level await (ES modules)

Inside ES modules (import/export), await can be used at the top level — no async function wrapper required. The module pauses until the awaited promise settles, and importing modules wait for it too. 

// config.mjs
const colors = fetch("../data/colors.json").then(r => r.json());
export default await colors;   // top-level await

// main.mjs — blocks until config.mjs finishes loading
import colors from "./config.mjs";
Top-level await is not supported in classic <script> tags or CommonJS (require) modules.

7. return await promise vs return promise

Two async functions that look similar behave differently on failure: 

// without await — shallow stack trace
async function noAwait() {
    return lastAsyncTask();
}
// Error at lastAsyncTask ONLY — noAwait is missing
// from the stack trace.
// with await — deep, useful stack trace
async function withAwait() {
    return await lastAsyncTask();
}
// Error at lastAsyncTask
//       at async withAwait  ← appears!
  • return await p re-throws the rejection into the current function, so the caller frame shows up in the stack trace — much easier to debug in test reports.
  • Contrary to popular belief, return await is at least as fast as return p — engines optimize native promise resolution.
  • Aside from stylistic reasons, return await is almost always preferable.

8. Awaiting serially vs in parallel

PatternTotal timeUse when
await a(); await b();sum of bothStep B depends on step A's result (login → dashboard)
await Promise.all([a(), b()])slowest oneIndependent calls run at the same time (parallel API smoke checks)
await Promise.allSettled([...])slowest oneIndependent calls, but you still want all results after failures
The sequential-await trap: const r1 = await p1; const r2 = await p2; waits for p1 first — but worse, p2 isn't wired into the chain until p1 settles. If p2 rejects early, it becomes an unhandled rejection even if you have a .catch(). For independent steps use Promise.all.

9. await in QA & Playwright

Every Playwright action is promise-based, so each one must be awaited. Forgetting an await often "works" but makes runs flaky — assertions may run on stale state. 

import { test, expect } from '@playwright/test';

test('checkout flow', async ({ page }) => {
    await page.goto('https://example.com');
    await page.click('#add-to-cart');

    // await the response from an API call inside the test
    const response = await page.request.get('https://api.example.com/order');
    const body = await response.json();

    await expect(body.status).toBe('created');
});
Real QA patterns: await in a retry loop for flaky APIs (with try/catch), await Promise.all for parallel health checks, and return await page.evaluate(...) to keep good stack traces in failure screenshots.

11. Common mistakes & interview traps

  • await in a non-async function → SyntaxError. (Check callbacks passed to forEach etc.)
  • Forgotten await → you get a promise object instead of the value: let title = page.title() vs let title = await page.title().
  • Awaiting independent calls sequentially → slow tests; use Promise.all.
  • Unhandled rejections with sequential awaits → see §8.
  • Believing return p equals return await p → stack traces differ on failure; prefer return await.
  • Assuming await blocks the page/thread → it never does; it only defers code after the await, while other code keeps running.
  • Awaiting inside forEach → callbacks fire in parallel-ish order; use a for...of loop for true sequencing.

12. Quick IQ questions (with answers)

Q: Where is await allowed?
A: Inside async functions, and at the top level of ES modules only.
Q: What does await 42 evaluate to?
A: 42 — non-promise values are auto-wrapped in a resolved promise and returned unchanged.
Q: Does await block the main thread?
A: No. It suspends only the surrounding async function and schedules a microtask to resume afterward.
Q: What happens if the awaited promise rejects?
A: The rejection reason is thrown at the await line; catch it with try/catch or attach .catch() before awaiting.
Q: return await p vs return p — any difference?
A: On failure, return await p includes the current function in the stack trace and is equally fast; prefer it for debuggable test failures.
Q: What's the output order?
console.log("A"); (async () => { await 0; console.log("B"); })(); console.log("C"); → A, C, B — the awaited part resumes as a microtask after the current synchronous work.
