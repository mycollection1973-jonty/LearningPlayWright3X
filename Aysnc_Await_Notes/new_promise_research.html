new Promise() — Full Research

A complete reference on the Promise constructor: the executor, resolve/reject, promise states, converting callback APIs, and QA/Playwright usage.

JavaScript · ECMAScript 2015 (ES6) · Baseline: July 2015

1. What is new Promise()?

The Promise() constructor creates a new promise object. Its main purpose is to wrap callback-based APIs that don't already return promises, converting them into modern, chainable, await-able code.

  • It must be called with new — calling Promise() without new throws a TypeError.
  • It accepts one function — the executor — which receives resolve and reject.
  • The executor runs synchronously, immediately at construction time.
  • If your task is already promise-based, you probably don't need this constructor at all — use Promise.resolve() or an async function instead.

2. Syntax

new Promise(executor)

function executor(resolveFunc, rejectFunc) {
    // some async operation that accepts a callback…
    // then call resolveFunc(value) on success
    //     or rejectFunc(reason) on failure
}
PartMeaning
executorA function run immediately by the constructor. Its return value is ignored; only calls to resolve/reject (or a thrown error) affect the promise.
resolveFunc(value)Fulfills the promise with value (or locks into a thenable / promise passed to it).
rejectFunc(reason)Rejects the promise with reason — same effect as throw in a try/catch sense.
Return valueThe new promise object (pending until resolved or rejected).

3. Promise states — pending, fulfilled, rejected

StateMeaningHandlers that fire
pendingNeither settled nor rejected — the operation is still running.none (yet)
fulfilledThe operation succeeded — resolve(value) was called with a non-thenable value..then(onFulfilled), await
rejectedThe operation failed — reject(reason) was called or the executor threw..catch(), try/catch around await
Resolved vs settled — don't confuse them: a promise can be resolved (someone called resolve()) but still be pending — exactly when it's resolved with another promise or thenable. The promise "locks into" that inner value and only settles when the inner one settles. Settled = fulfilled or rejected.

4. Executor rules — what actually happens

  • Runs immediately and synchronously with resolve and reject already "tethered" to the promise.
  • Return value is ignored. return "x" doesn't fulfill the promise — only calling resolve("x") does.
  • Throwing rejects — an uncaught error in the executor rejects the promise… unless resolve/reject already fired (then the throw is ignored).
  • First call wins. Only the first resolve() or reject() matters; later calls can never change the outcome.
  • If neither is ever called → the promise stays pending forever. (Note: pending promises don't prevent the program from exiting when the event loop is empty.)

Live example 1 — fulfill, reject, and first-call-wins

// 1. fulfill with a value
const p1 = new Promise(resolve => resolve("foo"));
p1.then(v => console.log(v));          // foo

// 2. reject with an error
const p2 = new Promise((resolve, reject) =>
    reject(new Error("Test failed")));
p2.catch(err => console.log(err.message));   // Test failed

// 3. throwing in the executor = calling reject()
const p3 = new Promise(() => { throw new Error("boom"); });
p3.catch(err => console.log(err.message));   // boom

// 4. only the FIRST resolve/reject wins
const p4 = new Promise((resolve, reject) => {
    resolve("first");
    reject(new Error("too late"));   // ignored
    resolve("again");                    // ignored
});
p4.then(v => console.log(v));          // first

console.log("before");

const p = new Promise((resolve) => {

console.log("after");

5. Resolving with a promise / thenable (flattening)

resolve(somePromise) doesn't copy the value — it locks your promise into that inner promise. Handlers you attach later wait for the inner one, and nested thenables get flattened automatically: 

const outer = new Promise(resolve => {
    resolve(new Promise(res => res("inner value")));
});

outer.then(v => console.log(v));   // inner value — no extra .then() needed

Equivalent to ~

new Promise((resolve, reject) => {
    try {
        thenable.then(v => resolve(v), r => reject(r));
    } catch (e) {
        reject(e);
    }
});
Danger — resolving with the promise itself: resolve(itself) causes a TypeError: Chaining cycle detected for promise (a cycle can never settle). Avoid patterns where the resolve value is the same promise you're creating.

6. Converting a callback API into a promise API

The single most important reason to use new Promise(). Given a classic callback-style API: 

readConfig("./config.json", (error, result) => {
    // everything that depends on the file must live in here
    if (error) reject(error);
    else console.log(result);
});
// code after this line runs immediately — it can't see `result`

Wrap it once, and callers get a clean promise:

function readConfigPromise() {
    return new Promise((resolve, reject) => {
        readConfig((error, result) => {
            if (error) reject(error);
            else resolve(result);
        });
    });
}

await readConfigPromise();   // readable, throwable, chainable

Live example 3 — wrap a simulated callback API

// A legacy, callback-based function (no promise support)
function lookupUser(id, callback) {
    // async work that reports back via callback(err, user)
    queueMicrotask(() => {
        if (id < 0) callback(new Error("invalid id"));
        else callback(null, { id, name: "QA User" });
    });
}

// Promise wrapper — the executor bridges callback → resolve/reject
function lookupUserAsync(id) {
    return new Promise((resolve, reject) => {
        lookupUser(id, (error, user) => {
            if (error) reject(error);
            else resolve(user);
        });
    });
}

lookupUserAsync(42)
    .then(user => console.log(user.id, user.name))          // 42 QA User
    .catch(err => console.log("Failed:", err.message));

lookupUserAsync(-1)
    .then(user => console.log(user))
    .catch(err => console.log("Failed:", err.message));  // Failed: invalid id

7. new Promise vs the alternatives

ToolUse it when…Example
new Promise(executor)Wrapping a callback-based API (fs, old libraries, browser XHR)readFile(path, cb) → promise
Promise.resolve(value)You already have a value / promise — just needs a promise shapePromise.resolve(200)
async functionYou control the code — simpler, auto-wraps the returnasync () => 200
Promise.withResolvers()You need resolve/reject outside the executor (e.g. decide resolution later)deferred-style flows
Rule of thumb: if the code inside the executor doesn't use a callback-based API, you probably shouldn't be using new Promise. Prefer an async function or Promise.resolve/reject.

8. new Promise in QA & Playwright

  • Promisify legacy helpers — wrap old Selenium-style or custom runner callbacks so tests can await them.
  • Custom waits — build a promise that resolves when a condition is met and rejects on timeout:
function waitForCondition(checkFn, timeoutMs = 5000) {
    return new Promise((resolve, reject) => {
        const start = Date.now();
        (function poll() {
            if (checkFn()) return resolve("condition met");
            if (Date.now() - start > timeoutMs)
                return reject(new Error("timed out waiting"));
            setTimeout(poll, 200);
        })();
    });
}

await waitForCondition(() => page.getByText("Loaded").isVisible());

9. Common mistakes & interview traps

  • Forgetting new → Promise(...) throws TypeError: Constructor Promise requires 'new'.
  • return instead of resolve() → the return value is ignored; the promise stays pending forever.
  • Never calling resolve/reject → forever-pending promise; handlers never fire. (A pending promise doesn't block program exit, though.)
  • Resolving with the promise itself → chaining-cycle TypeError.
  • Calling resolve and reject → first call wins; the rest are silent no-ops, so guard logic around "has it settled yet?" is unnecessary.
  • Throwing after resolve() → the throw is swallowed (promise already resolved).
  • Using new Promise where async/Promise.resolve suffice → more code, more chances for a forever-pending bug.

10. Quick IQ questions (with answers)

Q: When is the executor function called?
A: Immediately and synchronously when the promise is constructed — before the constructor even returns.
Q: Does return "x" inside the executor fulfill the promise?
A: No. The executor's return value is ignored; only calling resolve("x") fulfills it.
Q: What happens if the executor throws?
A: The promise rejects with the thrown error — unless resolve/reject were already called, in which case the throw is ignored.
Q: resolve(a) then reject(b) — what state?
A: Fulfilled with a. Only the first call affects the promise; every later call is ignored.
Q: What does resolve(anotherPromise) do?
A: It "locks in" your promise to anotherPromise — your promise stays pending until that inner promise settles, and adopts its result without extra .then().
Q: Can I access resolve/reject after the constructor returns?
A: Not from the executor scope. Use Promise.withResolvers() if you need the resolving functions later.
