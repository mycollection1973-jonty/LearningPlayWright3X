The Callback Pattern — Full Research

A complete reference on callback functions in JavaScript: sync vs async callbacks, error-first style, callback hell, and how they evolved into promises & async/await.

JavaScript · Core language concept · Callbacks are as old as JS itself

1. What is a callback function?

A callback function is a function passed into another function as an argument, which the outer function then invokes ("calls back") to complete some routine or action.

  • You write the function (the consumer of a callback-based API).
  • The API (the caller / provider) takes your function and executes it at the right moment.
  • The API controls the parameters passed into your callback — and may use your callback's return value to guide its own behavior.

The canonical shape:

function doSomething(callback) {
    // ...do work...
    callback();   // "calls back" the function you passed in
}

doSomething(() => console.log("inside the callback"));

2. Synchronous vs asynchronous callbacks

Callbacks can be invoked in two very different ways — and knowing which one you're dealing with decides how your code behaves:

Synchronous callbackAsynchronous callback
Called when?Immediately, during the outer function call — same tickLater, after an async operation finishes
ExamplesArray.map(), Array.forEach(), Array.filter(), Array.sort()setTimeout, fs.readFile, event listeners, fetch().then()
Code after the call runs…after the callback finishedbefore the callback runs
The side-effect trap (classic interview puzzle): 
let value = 1;

doSomething(() => { value = 2; });

console.log(value);   // 1 or 2? — depends on sync vs async!

If doSomething calls the callback synchronously → logs 2. If it defers the call (asynchronously, like setTimeout(cb, 0)) → logs 1, because the callback hasn't run yet.

Live example 1 — sync vs async timing in action

let value = 1;

// SYNC version — callback runs immediately
function doSync(callback) { callback(); }

// ASYNC version — callback deferred to a microtask
function doAsync(callback) { queueMicrotask(callback); }

doSync(() => { value = 2; });
console.log("after sync call:", value);   // 2 — already ran

doAsync(() => { value = 3; });
console.log("right after async call:", value);  // 2 — callback hasn't run yet

queueMicrotask(() => console.log("after async callback:", value));  // 3

3. Ways to write a callback

// 1. Named function
function onLoad(data) { console.log(data); }
fetchData(onLoad);

// 2. Anonymous function expr
fetchData(function (data) {
    console.log(data);
});
// 3. Arrow function (most common)
fetchData(data => console.log(data));

// 4. Method reference
const logger = { log: d => console.log(d) };
fetchData(logger.log);

4. The error-first callback convention (Node.js)

Node-style APIs follow a strict convention so every callback knows where the error lives: the first parameter is the error (or null), and the result comes after it: 

readFile("./config.json", (error, result) => {
    if (error) {
        console.error("Failed:", error.message);
        return;               // stop early on error
    }
    console.log(result);   // error was null — safe to use result
});

The callback must check the error first, because a non-null error means result is meaningless.

Live example 2 — error-first callback pattern

function lookupUser(id, callback) {
    // simulates an async DB lookup
    queueMicrotask(() => {
        if (id < 0) {
            callback(new Error("invalid id"), null);
        } else {
            callback(null, { id, name: "QA User" });
        }
    });
}

// consumer side — always check error FIRST
lookupUser(42, (error, user) => {
    if (error) return console.log("Error:", error.message);
    console.log(user.id, user.name);   // 42 QA User
});

lookupUser(-1, (error, user) => {
    if (error) return console.log("Error:", error.message);  // Error: invalid id
    console.log(user);
});

5. The "I can't return a value" trap

One of the most confusing things about callbacks: you cannot return a value from an async callback — by the time the callback runs, the outer function has already returned. 

// WRONG — returns undefined!
function getConfig() {
    let config;
    readFile("./config.json", (err, data) => { config = data; });
    return config;   // undefined — the callback hasn't run yet
}

// RIGHT — consume the value inside the callback, or wrap in a Promise
function getConfigAsync() {
    return new Promise((resolve, reject) => {
        readFile("./config.json", (err, data) => {
            if (err) reject(err); else resolve(data);
        });
    });
}
This trap is exactly why Promises were created — see the Promise series of pages in this folder.

6. Callback hell — the pyramid of doom

When steps depend on each other, each callback must nest inside the previous one. Levels of nesting grow with each step, and the code drifts to the right — "the pyramid of doom":

Live example 3 — nested sequential callbacks

// Simulated async step that calls back with a label
function step(name, next) {
    queueMicrotask(() => next(name));
}

// Each step depends on the previous one → nested callbacks
step("Open browser", s1 => {
    step("Login", s2 => {
        step("Run test", s3 => {
            step("Teardown", s4 => {
                console.log(s1 + " → " + s2 + " → " + s3 + " → " + s4);
            });
        });
    });
});
// Open browser → Login → Run test → Teardown

Four real problems with this shape:

  • Readability — indentation depth grows with every dependent step.
  • Error handling — every level needs its own if (err) check.
  • Inversion of control — the API decides when your code runs (and whether it runs at all).
  • Fragility — mixing one async call with sync logic is easy to get wrong.

7. The evolution: callbacks → promises → async/await

// 1. Callbacks — nested, hard to read
step1(x => {
    step2(x, y => {
        step3(y, z => console.log(z));
    });
});

// 2. Promises — flat chains
step1()
    .then(x => step2(x))
    .then(y => step3(y))
    .then(z => console.log(z));

// 3. async/await — reads like synchronous code
async function run() {
    const x = await step1();
    const y = await step2(x);
    const z = await step3(y);
    console.log(z);
}

Same three steps, three generations of syntax. The goal was always the same: "do step 2 after step 1 finishes" without letting code sprawl to the right.

8. Callbacks in QA & Playwright

  • Playwright prefers promises — page.waitForFunction(), listeners and hooks still accept callbacks:
await page.waitForFunction(() => document.querySelector("#spinner") === null);

page.on("console", msg => console.log(`[page]`, msg.text()));
page.on("response", res => {
    if (res.status() === 503) failures.push(res.url());
});

await page.evaluate((num) => Math.pow(num, 2), 4);  // callback runs in the page
  • Custom retry with callbacks — poll a condition until it's true or the deadline passes (see the new Promise page for the wrapped version).

9. Common mistakes & interview traps

  • Calling the callback instead of passing it → setTimeout(cb(), 1000) runs cb() immediately and passes its return value. Pass the reference: setTimeout(cb, 1000).
  • Forgetting the error-first check → using result when error is truthy.
  • Trying to return from an async callback → the outer function already returned; you get undefined.
  • Not realizing the callback fires later → code after the API call runs before your callback; guard against stale state.
  • Abusing forEach + async callbacks → forEach doesn't wait; it fires all callbacks immediately. Use a for...of loop or Promise.all for sequencing.
  • Swallowing the error → an error-first callback that ignores error hides real failures from your test run.

10. Quick IQ questions (with answers)

Q: What is a callback function?
A: A function passed as an argument to another function, which the receiving function invokes to complete an action.
Q: Sync or async — how are the callbacks of map, forEach, setTimeout, and .then() called?
A: map/forEach call back synchronously; setTimeout/then call back asynchronously (later, in a task/microtask).
Q: Why does this log 1 instead of 2?
let v = 1; setTimeout(() => v = 2, 0); console.log(v); → the callback is deferred; console.log(v) runs first. Order would be the opposite for a sync API.
Q: What is the error-first callback convention?
A: The callback's first parameter is the error (or null); the result follows. Always check the error before using the result. Standard in Node.js APIs.
Q: Can I return a value from an async callback?
A: No — the outer function has already returned. Consume the value inside the callback, or wrap the API in a new Promise.
Q: How do you escape callback hell?
A: Promises flatten the nesting into chains; async/await flattens it again into straight-line code.
