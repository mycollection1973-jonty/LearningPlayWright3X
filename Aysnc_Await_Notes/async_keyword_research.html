The async Keyword — Full Research

A complete reference on async functions in JavaScript: what they are, how they behave, and how to use them in QA / Playwright automation — with a dedicated Playwright examples section.

JavaScript · ECMAScript 2017 (ES8) · Baseline: April 2017

1. What is the async keyword?

async is a keyword placed before a function to mark it as an asynchronous function. Its job is simple: it makes the function always return a Promise, and it enables the await keyword to be used inside the function body.

Defining a function as async:

  • Always returns a Promise — even if you return a plain value.
  • Allows await inside its body to pause execution until a promise settles.
  • Lets you handle async errors with ordinary try/catch — no more .catch() chains.
  • Creates an AsyncFunction object under the hood.

2. Syntax — all 5 forms

async function name(param1, param2) {
    // ...body
}
const name = async function (param) {
    // function expression
};
const name = async (param) => {
    // async arrow function
};
const obj = {
    async method() { /* object method */ }
};
class Runner {
    async run() { /* class method */ }
}
Gotcha — line terminator: you cannot put a line break between async and function, otherwise Automatic Semicolon Insertion (ASI) treats async as a plain identifier and the line as a normal function declaration.

3. The one rule that explains everything

An async function ALWAYS returns a Promise.

If you return a plain value, it is automatically wrapped using Promise.resolve(). If you throw, the function returns a rejected promise.

What you write (return …)What the caller receives
return 1;Promise.resolve(1)
return "Pass";Promise.resolve("Pass")
return Promise.resolve(200);Promise.resolve(200) (already a promise)
throw new Error("boom");Rejected promise (error)
no return statementPromise.resolve(undefined)

Live example — run it below

async function getTestResult() {
    return "Pass";   // plain value → wrapped
}

getTestResult().then(result => {
    console.log(result);          // Pass
});

async function getStatus() {
    return { status: 200, body: "Created" };
}

getStatus().then(res => {
    console.log(res.status, res.body);  // 200 Created
});
Reference identity gotcha: asyncReturn() returning an existing promise p gives you a different reference than p itself, whereas Promise.resolve(p) returns the same reference. Don't compare promise identity against an async function's return value.

4. Execution order — synchronous start, asynchronous finish

Think of an async function's body as split by await expressions:

  • Top-level code up to the first await runs synchronously — immediately, in the same tick as the call.
  • When await is hit, the function is suspended and control returns to the caller.
  • After the awaited promise settles, execution resumes inside a microtask (code after await behaves like a .then() callback).
  • An async function with no await at all runs completely synchronously (but still returns a promise).

Live example — order of logs

console.log(1);  // sync

async function test() {
    console.log(2);            // sync part of the async fn
    await Promise.resolve(); // yield control here
    console.log(3);            // resumes as a microtask
}

test();
console.log(4);  // sync

// Order: 1 → 2 → 4 → 3

Live example — async with NO await runs synchronously

async function noAwait() {
    console.log("runs synchronously");   // no await inside
    return "value";
}

console.log("before call");
noAwait().then(v => console.log("promise resolved:", v));
console.log("after call");

// before call
// runs synchronously
// after call
// promise resolved: value

Live example — one await makes two calls interleave

async function callApi(name) {
    console.log(name, "started");
    await 0;   // a single await yields control
    console.log(name, "finished");
}

callApi("Login API");
callApi("Profile API");

// Login API started
// Profile API started
// Login API finished
// Profile API finished

5. async + await together

  • await is only valid inside an async function (or in ES modules at top level). Using it elsewhere throws SyntaxError.
  • await somePromise suspends the function until the promise settles.
  • The resolved value becomes the result of the await expression.
  • If the awaited promise rejects, the rejection is thrown at the await line — catch it with try/catch.

6. Sequential vs parallel execution

PatternBehaviorUse when
await a(); await b(); Second request starts only after first completes (total time = sum) Step 2 depends on Step 1's result — e.g. Login → Dashboard
start both, then await Timers run concurrently, awaits still resolve in order Both needed, no dependency — but risky for rejections
await Promise.all([a(), b()]) Both start at once; waits for all; fails fast with the first rejection Independent steps, e.g. parallel API smoke calls
await Promise.allSettled([...]) Waits for all; never rejects; reports each outcome You want results even when some fail

Live example — sequential vs parallel timing

const sleep = ms => new Promise(res => setTimeout(res, ms));

async function sequential() {
    console.log("SEQ 1: first API call started");
    await sleep(50);
    console.log("SEQ 2: first done, second started");
    await sleep(50);
    console.log("SEQ 3: both done (~100ms total)");
}

async function parallel() {
    console.log("PAR 1: both calls started together");
    await Promise.all([sleep(50), sleep(50)]);
    console.log("PAR 2: both done (~50ms total)");
}

sequential();
parallel();
// SEQ 1: first API call started
// PAR 1: both calls started together
// SEQ 2: first done, second started
// PAR 2: both done (~50ms total)
// SEQ 3: both done (~100ms total)
Unhandled rejection trap: with const r1 = await p1; const r2 = await p2;, p2 is not wired into the promise chain until p1 settles. If p2 rejects before that, you get an unhandled rejection even though the caller has a .catch(). Use Promise.all / Promise.allSettled for concurrent work.

7. Error handling — try / catch / finally

Live example — catching a rejected promise

async function withTryCatch() {
    try {
        let data = await Promise.reject("503 Service Unavailable");
        console.log(data);
    } catch (err) {
        console.log("caught:", err);
    } finally {
        console.log("cleanup done");
    }
}

async function withCatch() {
    let response = await Promise.reject("Request failed")
        .catch(err => err + " → fallback");
    console.log(response);
}

withTryCatch();
withCatch();
// caught: 503 Service Unavailable
// cleanup done
// Request failed → fallback

This mirrors promise behavior: try → .then(), catch → .catch(), finally → .finally(). The big win: straight-line, synchronous-looking error handling.

8. Hoisting

async function declarations are hoisted like regular function declarations — you can call them anywhere in their scope, even before the declaration line appears. 

runTest();  // works — declaration is hoisted

async function runTest() {
    await Promise.resolve("Login OK");
}

Async function expressions and arrows are not hoisted — same as regular function expressions.

9. async in QA & Playwright — full examples

Playwright's test runner is built on async/await: the test body, the hooks, the request fixture, custom fixtures, and even assertion retries are async functions. Understanding the async keyword is what makes Playwright code readable instead of a promise-chain maze.

About the examples below: Playwright snippets need the @playwright/test runner and a live app/API, so they are shown as reference patterns (not runnable here). The pure-JS runnable examples are the numbered cards above.

9.1 Why every Playwright test is async

Every page action returns a promise. Marking the test callback async lets you await each one, so the test reads top-to-bottom like a manual test script. Forgetting await often "works" but makes runs flaky — assertions may run on stale state. 

import { test, expect } from '@playwright/test';

test('user can log in', async ({ page }) => {
    await page.goto('https://example.com/login');
    await page.fill('#username', 'qa_user');
    await page.fill('#password', 'secret');
    await page.click('button[type=submit]');

    await expect(page).toHaveURL(/dashboard/);
    await expect(page.locator('.welcome')).toContainText('qa_user');
});

9.2 Async lifecycle hooks — setup and teardown

beforeEach / afterEach / beforeAll / afterAll receive the same fixtures and are async for the same reason: they must await their setup work before the test body runs. 

import { test, expect } from '@playwright/test';

test.beforeEach(async ({ page }) => {
    await page.goto('https://example.com/app');
    await page.evaluate(() =>
        localStorage.setItem('token', 'test-token')
    );
});

test.afterEach(async ({ page }) => {
    await page.evaluate(() => localStorage.clear());
});

test('dashboard loads', async ({ page }) => {
    await expect(page.locator('.dashboard')).toBeVisible();
});

9.3 Async API testing with the request fixture

The request fixture is an async API client — every call returns a promise whose .json() is also async. Chained awaits make request → assert flows flat. 

import { test, expect } from '@playwright/test';

test('create order via API, then verify it', async ({ request }) => {
    const createRes = await request.post('https://api.example.com/orders', {
        data: { product: 'laptop', qty: 1 },
    });
    expect(createRes.status()).toBe(201);

    const orderId = (await createRes.json()).id;

    const getRes = await request.get('https://api.example.com/orders/' + orderId);
    expect(getRes.ok()).toBeTruthy();
    await expect(getRes.json()).resolves.toMatchObject({ product: 'laptop' });
});

9.4 Retrying with expect.poll — async polling

expect.poll takes an async callback and re-invokes it over and over until it returns the expected value or the timeout is reached — perfect for asserting on the outcome of background jobs you can't wait on directly. 

import { test, expect } from '@playwright/test';

test('order reaches SHIPPED after async processing', async ({ request }) => {
    await request.post('https://api.example.com/orders', {
        data: { product: 'laptop' },
    });

    // async callback is polled until it returns 'SHIPPED' or times out
    await expect.poll(async () => {
        const res = await request.get('https://api.example.com/orders/status');
        return (await res.json()).status;
    }, { timeout: 10000 }).toBe('SHIPPED');
});

9.5 Parallel work inside a test — Promise.all

When a page load triggers several API calls, set up all the waitForResponse promises first, then let Promise.all run them concurrently with the navigation. 

import { test, expect } from '@playwright/test';

test('dashboard fires two APIs — wait for both', async ({ page }) => {
    const [userRes, statsRes] = await Promise.all([
        page.waitForResponse(r => r.url().includes('/api/user')),
        page.waitForResponse(r => r.url().includes('/api/stats')),
        page.goto('https://example.com/dashboard'),
    ]);

    expect(userRes.status()).toBe(200);
    expect(statsRes.status()).toBe(200);
});

9.6 Reusable async helper — retry wrapper for flaky endpoints

A classic QA pattern: wrap a flaky call in an async retry loop using try/catch and a backoff delay. Note the return await fn() — it keeps the full stack trace if the last attempt fails. 

// Reusable async retry wrapper — real QA pattern for flaky endpoints
async function retry(fn, attempts = 3, delayMs = 1000) {
    for (let i = 1; i <= attempts; i++) {
        try {
            return await fn();
        } catch (err) {
            if (i === attempts) throw err;
            console.log(`Attempt ${i} failed (${err.message}) — retrying…`);
            await new Promise(res => setTimeout(res, delayMs));
        }
    }
}

test('flaky API call succeeds after retries', async ({ request }) => {
    const data = await retry(async () => {
        const res = await request.get('https://api.example.com/flaky');
        if (!res.ok()) throw new Error('503 Service Unavailable');
        return res.json();
    }, 3, 500);

    expect(data).toBeDefined();
});

9.7 Custom async fixture — login once, teardown after

Playwright fixtures are async functions receiving use. Everything before await use(value) is setup; everything after runs as teardown — a clean wrapper for token management. 

import { test as base, expect } from '@playwright/test';

// Custom async fixture: logs in once per test and cleans up after
export const test = base.extend({
    authToken: async ({ request }, use) => {
        const res = await request.post('https://api.example.com/login', {
            data: { user: 'qa', pass: 'secret' },
        });
        const { token } = await res.json();
        await use(token);   // hand the value to the test
        // teardown runs after the test body finishes
        await request.post('https://api.example.com/logout');
    },
});

test('calls profile API with the token', async ({ authToken, request }) => {
    const res = await request.get('https://api.example.com/profile', {
        headers: { Authorization: `Bearer ${authToken}` },
    });
    expect(res.ok()).toBeTruthy();
});
Common real-world patterns: retry flaky APIs with an async retry wrapper + try/catch; run independent API smoke tests with Promise.all; sequence dependent steps (login → dashboard → report) with plain await.

11. Common mistakes & interview traps

  • Using await outside async fn → SyntaxError. (Allowed at top level of ES modules.)
  • Forgetting that async fn returns a promise → const x = asyncFn() is a promise, not the value. You must await it.
  • Line break between async and function → ASI silently breaks the declaration.
  • Awaiting sequential-independent calls → wastes time; use Promise.all.
  • No catch on concurrent awaits → unhandled rejections (see section 6).
  • Comparing promise identity with an async fn return → always false.
  • Not handling rejections at all → crashes / unhandled-rejection warnings in Node.
  • Playwright: missing await on an action or assert → the action starts but the test moves on; flaky, hard-to-reproduce failures. Always await actions and expect.
  • Playwright: await inside forEach → callbacks fire in parallel-ish order; use for...of for true sequencing.
  • Playwright: beforeEach not awaited → race between setup and test body; hooks must be async and awaited internally.

12. Quick IQ questions (with answers)

Q: Does an async function always return a Promise?
A: Yes — plain return values are wrapped in Promise.resolve(); thrown errors produce a rejected promise.
Q: What does await do to the function's execution?
A: It suspends the async function, yields control back to the caller, and resumes (in a microtask) once the awaited promise settles.
Q: What logs and in what order?
console.log("A"); async function t(){ console.log("B"); await 0; console.log("C"); } t(); console.log("D"); → A, B, D, C — first await defers "C" to the microtask queue.
Q: Is async function hoisted?
A: Yes, like regular function declarations. Async function expressions are not hoisted.
Q: async/await vs promises — is it a different technology?
A: No. async/await is syntactic sugar built on the same Promises; behavior is similar to combining generators with promises.
Q: When must you use Promise.all instead of sequential await?
A: When steps are independent (parallel) and to guarantee rejections happen inside a wired-up chain — avoiding unhandled rejection errors.
Q: Why is a Playwright test callback declared async?
A: Because every page action and assertion returns a promise. The async keyword lets the runner await the whole flow and report the failure correctly.
Q: Why does expect.poll accept an async function?
A: It re-invokes the async callback on every poll until it returns the expected value or the timeout expires — ideal for asserting on background/async job results.
